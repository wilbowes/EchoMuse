# UAT — controller 2.26.0 and firmware v2.18.0

## About this report

**What:** user acceptance testing (UAT) is the last check before a release: does the software do what it says, on real hardware, the way someone would use it. Automated tests check the code; this checks the product.

**Why:** settings that saved and then did nothing have shipped before. Every EchoMuse release now gets this pass, and the report ships with it.

**How:** a script drives the dashboard in a browser and changes every setting, then reads each Echo to confirm it received and applied the change, and puts it back. An accessibility scanner checks every screen. A person then works through voice, music, buttons and pairing with the Echoes in front of them, while the logs are watched.

**PASS.** 46 dashboard controls checked on 3 real Echoes: 4 disabled, 17 received, 25 applied. Accessibility: 22 views, all clean (WCAG 2.1 AA, automated).

Guided steps with a person: 24 pass, 2 pass after fix, 5 pass with findings, 3 not run

**Versions.** This is the acceptance run for the GA pair, controller 2.26.0 and firmware v2.18.0. It was run on 2026-10-11 against the Early Access builds they are cut from: the day began on controller 2.26.0-ea.2 with firmware v2.18.0-ea.2, two faults found here were fixed, and the automated run and both wizard runs were repeated on controller 2.26.0-ea.3 with firmware v2.18.0-ea.3. The GA builds are that code with the release's version number. Hands-on steps from before the fixes were not repeated unless a fix touched them.

Echoes: `…1VVV` (FireOS 5), `…15LE` (emOS, 32-bit kernel), `…0C95` (emOS, 64-bit kernel).

## Findings

Fixed before release:
- **A muted Echo could come back unmuted after a power cut.** With the power pulled within a few seconds of the mute press, two of three Echoes started up listening. The mute state was not being forced to flash. Fixed in #849 (firmware v2.18.0-ea.3) and retested on all three: mute and unmute each survived a power cut within 2 seconds, twice each way.
- **The provisioning wizard did not say why a step failed.** On an Echo without `f1r30s.zip` on its storage, step 3 failed with "Click Retry first" and offered to restore a boot image that had never been taken; step 1 printed an error telling the tester to delete an Echo above a button that kept it. Fixed in #850 (controller 2.26.0-ea.3): the failure box gives the reason, step 3 asks for the file and checks it, and step 1 offers its two choices. Both wizards were then run end to end, FireOS on a stock FireOS 5 Echo and emOS on a stock FireOS 6 Echo.

Known issues in this release:
- **An Echo that restarts and rejoins a playing Sendspin group can fall out of sync until the next track.** Heard as an echo on lyrics while both players reported under 0.4 ms of error. Cause not found; to be investigated after this release.
- **A fleet setting saved while an Echo holds its own value for it changes nothing on that Echo**, and the fleet page does not say so. Found on Response level.
- **The controller stalls for a few seconds while updating several Echoes' firmware at once** (4.4 s and 3.2 s measured). An Echo speaking at that moment would stutter.
- **The ring leaves "thinking" before the reply is heard.** Audio follows about half a second later, and on two turns one to two seconds later.
- **A wake word said during a ringing timer can be taken by a different Echo** from the one ringing. The ring still pauses and resumes correctly.
- **A command run straight on from the wake word can still lose its first word**: 1 of 4 with speech deliberately run together.
- **The pairing hold fires on an Echo that is already paired and connected** (#841).
- The ring's volume level scaling reads wrong to the tester.

Not covered: talking over a reply while Home Assistant is unreachable (#417), the Bluetooth proxy feeding Bermuda while music plays, a Bluetooth connection through the proxy, and the database migration on a database holding real data (run on an empty one). Pausing music by voice failed inside Home Assistant, which transcribed the command correctly and sent no media command.

## How this was run

- Controller image `ghcr.io/wilbowes/echomuse-controller:2.26.0-ea.3`, isolated rig (tools/uat/rig.py); Echoes attached over USB: `…15LE` (emos), `…0C95` (emos), `…1VVV` (fireos).
- Controls run 2026-10-11T06:16:39Z; accessibility scan 2026-10-11T06:17:08Z.
- Each control: changed in the browser, saved, read back from the API, then checked on the Echo (`/tmp/em-config.json`: received, and applied where its running config covers the key), then put back and checked again.
